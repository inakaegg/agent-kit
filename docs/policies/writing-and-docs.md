# 文書の執筆担当と構成の規則

共通 `AGENTS.md` §3・§5 の骨子を前提とする。本ファイルは文書を新規作成・実質更新・再編するとき、およびタスク記録を作成するときに読む。手順は `$docs-maintenance`、用語は本kitの `docs/terminology-ja.md` に従う。外部の文章作成Skillは利用可能な場合だけ補助として使い、未導入でも本規則と `$docs-maintenance` で続行する。

## 執筆担当の判定

- 文書の執筆担当は、pathや拡張子ではなく**主な読者**で判定する。人間を主な読者・承認者・成果物の受け手とする文書（README、利用者向けdocs、製品仕様、設計文書、設計判断の記録、release note、人間がreviewする提案・調査報告など）の新規作成と本文の実質的な更新は、そのタスクを担当しているセッション自身が執筆・編集しなければならない。担当セッションとは、ユーザーが対話しているClaude CodeまたはCodexのセッション、またはユーザーが許可した並行体制で対象ファイルの執筆を割り当てられた独立した対話席を指す。監視役は本文を執筆しない。人間とAIの双方が正式に使う文書、および主な読者を判定できない文書も、人間向けとして扱う。
- 人間向け文書のうち、設計・仕組みをユーザーへ平易に説明する解説文書は、利用可能な範囲で最上位の深い思考用モデル（`WRITING_MODEL_DEEP` が示す担当。agent-settings、`AGENTS.md` §1）のセッションが、対象の仕組みを自分で理解したうえで執筆する。他のセッションは素材（実測値・実例）の提供までとする。
- AI・agentだけが使う文書（task契約、active plan、引き継ぎ、prompt、機械処理用の文書）は、サブエージェントや別セッションのagentが作成・更新してよい。ただし規則ファイル（共通 `AGENTS.md`、projectの `AGENTS.md`・`CLAUDE.md`）の本文編集は、原則として `WRITING_MODEL_DEEP` が示す担当のセッションだけが行う。他のセッションは変更案の提示までとする。
- 人間向け文書について、担当セッション以外のagent（サブエージェント、未割当の別セッション、レビュー担当）は事実確認、要件・制約の整理、担当セッションへ渡す入力の作成、生成された差分のreview、command・link・testの検証を担当してよく、最終本文を代筆してはならない。担当セッションが利用不能、権限不足、またはそのターンで実行を許可されていない場合は、別agentが代筆せず停止して理由を報告する。

執筆担当の `WRITING_MODEL_DEEP` も `CLI:MODEL(EFFORT)` の候補順で設定する。選択はmodel resolverを使い、利用不能時の切り替えと記録は `review.md` の設定解決規則に従う。執筆とレビューの候補は別々に設定できる。

## 文書構成の既定

プロジェクトが別の構成を定めていない場合、次を既定とする。

- `README.md` — 主文書。初見の人に伝えたいこと（何を作るか、方向性、構成図、技術構成、動かし方）を書き、詳細は `docs/` へリンクする。目次だけの README にしない。公開する（または公開予定の）repositoryでは `README.md` を英語にし、冒頭で `README.ja.md` へリンクする。日本語版を正本として先に確定し、英語版はそれに同期する。
- `docs/` — 詳細の正本。データ項目の定義、仕組みの説明、費用の設計など。
- `docs/decisions/` — 設計判断の記録。`001-DynamoDBを採用する.md` のように番号と「何を決めたか」の平叙文で名付け、決めた内容・理由・検討した代替案・トレードオフを短く残す（ADRと呼ばれる形式）。
- `docs/CLI.md` — 貼ればそのまま動くコマンドの表。
- `docs/ROADMAP.md` — 実装の順序と進み具合。
- プロジェクトの `AGENTS.md`・`CLAUDE.md` には、そのプロジェクト固有の規則の差分だけを書く。技術選定・仕様・データの扱いは文書側（README・docs/）に属し、規則ファイルへ書かない。

## 図解とロゴの既定

- README・SPEC・解説文書の新規作成と大きな再編では、概要と、文章だけでは伝わりにくい要所（運用形態の比較、状態遷移、構成、経路など）に図解を入れることを既定とする。既存文書の部分更新では、更新箇所が図で分かりやすくなるときに追加を提案する。
- 図はローカル生成に限る。流れ・状態・比較はMermaid（GitHubがそのまま描画する）、アイコン付き構成図はdiagrams→SVGとし、選び方と作り方は `$architecture-diagram` に従う。外部の画像生成サービスや課金APIを図解に使わない。正本は生成スクリプトまたはMermaid本文で、出力画像を手で編集しない。
- 配布・公開を想定するrepo（プラグイン、ライブラリ、CLI等）のREADME冒頭にはロゴを置くことを既定とする。ロゴは手書きSVG等のローカル生成とし、`assets/` に正本をcommitして両言語のREADMEから参照する。
- 個人使用・内部repoではロゴを省略してよい。図解は、`DOCS_LEVEL=minimal` でも本来必要な構成図・経路図を省略しない。プロジェクトが文書を最小にする方針を定めている場合はそちらを優先する。

## 状態記述は1箇所

実装状況・進み具合・「現状は〜」の類を書く場所は `docs/ROADMAP.md`（またはプロジェクトが定めた1箇所）に限る。各文書の冒頭に更新日を置かない。状態の注記を複数の文書へ撒くと、書いた瞬間から腐り始め、更新の手間だけが増える。文書本文は設計と仕様を書き、状態はROADMAPと git 履歴に任せる。

## 用語の選び方

- 日本の開発現場で一般的でない英語圏のソフトウェア工学用語・略語を、説明なしに導入しない。
- 日本語で広く定着したカタカナ語（API、フォールバック、キャッシュ、リファクタリング等）はそのまま使う。
- 英語の直訳で日本語としてかえって分かりにくくなる語（例：regressionの「回帰」単独使用）は、日本のエンジニアが一般的に使う表現を優先する。
- 対応表は本kitの `docs/terminology-ja.md`。表にない語も上の3原則で自分で判断し、書いた本人が推敲する。禁止語辞書を増やし続けることを対策にしない。
- 二言語で併記する文書の日本語版は、文単位の翻訳ではなく日本語として書き下ろす。原文の比喩・術語を逐語で写して日本語に新語を作らない（例: seat→「席」、floor→「床」）。訳語は役割・機能を表す日本語の普通の言い方を選ぶ。

## 既存記述の引き継ぎ時の再検証

文書を書き直す・移設する・翻訳するとき、既存文書から引き継ぐ文も新規記述と同じ検証対象とする。特に出自・経緯、他リポジトリの状態、「〜が正本」、バージョン、日付などの事実主張は、引き継ぐ前に現物（対象リポジトリの実ファイル・commit履歴・設定）で確認する。古い文書に書いてあること自体を根拠にしない。大きな意思決定をしたら、その時点で `docs/decisions/` に理由と代替案を残す（残さないと、後続の書き直しが古い記述を検証する手掛かりを失う）。

## 文書更新のレビュー

人間向け文書の新規作成と本文の実質的な更新は、`READABILITY_REVIEW=true` のとき、`REVIEW_MODEL_READABILITY` が示す担当の、履歴を共有しない別セッションによる読みやすさレビューを通してからcommitする。誤字修正・リンク修正等の軽微変更は対象外。公開前の読みやすさレビューはこれとは別の公開前の関門で、`docs/policies/git-and-remote.md` に従う。`DOCS_LEVEL=minimal`（既定値。非公開・非共有repo向け）のrepoでは、文章の詳細化を免除し、人間向け文書は骨組みか要点の箇条書きまでに留め、読みやすさレビューを課さない。公開・共有repoは追跡対象の agent-settings.env で `full` にする。既に公開・共有しているrepoで値が未設定なら、既定値によらず `full` として扱い、気づいた時点で明記する。本kit自身は公開のため `full` 扱いとする。本来必要な構成図・経路図は免除しない。公開する時点で、追跡対象の設定を `full` に戻し、骨組みを完成文書へ整え、読みやすさレビューを通してから公開する（`docs/policies/git-and-remote.md`）。レビューの回数・指摘の扱いは本kitの `docs/policies/review.md` に従う。

## タスク記録の配置

配置判断の入口は `docs/instruction-placement.md`、タスク記録の詳細の正本は本節とする。

`_ai/` は常にmain checkout側のdirectoryを正本とし、linked worktreeの側へ置かない（git管理外のため、worktreeの削除と同時に記録を失う）。

worktreeで作業するタスクの契約・計画・レビュー資料もmain checkout側の `_ai/tasks/` へ書く。`_ai/` の内部はタスク単位で分ける。ディレクトリ名は「開始日-slug」（例 `2026-08-25-search-api`）とし、slugは原則そのtaskのbranch名と揃える（既存の日付なしdirectoryは改名しなくてよい）。契約は `_ai/tasks/<開始日-slug>/TASK.md`、作業状態は同directoryの `active-plan.md`、受け渡し・レビュー資料も同directory（レビューは `reviews/` 配下）へ集める。

`TASK.md` の冒頭にbranch名・期間・結果（完了/中止/引き継ぎ先）を1行ずつ書く。別タスクの契約・計画ファイルを上書き・転用せず、同じbranch・worktreeで複数タスクが並行する場合もタスクごとに別directoryを使い、着手時に既存directoryを確認して重複しないslugを選ぶ。既存のSkill・テンプレートにある `_ai/TASK.md` という表記は、現在のタスクの契約ファイルを指すと読み替える。

`_ai/` へ置くのは、契約・作業状態、受け渡し、独立レビュー資料の3種だけとする。タスク完了後もdirectoryは過去記録として残すが、完了済みタスクの文書を現在の契約として読まない。増えて見通しが悪くなったら、削除ではなく整理（アーカイブ等）をユーザーへ提案する。

進行中タスクの調査、分析、経過報告はチャット履歴に残し、ファイルにしない。チャット履歴だけを永続仕様の正本にしない。実装後も必要な仕様・合意・制約は、適切なリポジトリ内文書へ残す。

## 契約の内容

契約の重さは `AGENTS.md` §7の区分に連動させる。動作に影響する小さな変更は契約なし、通常対象作業は目的・合格条件・検証の3項目、重リスク作業は目的、範囲外、合格条件、検証、停止条件の全項目を `_ai/tasks/` 配下の `TASK.md` へ書く。同じ機能を扱う既存の設計文書・対応表がある場合は、その該当制約を仕様へ転記し、破棄する制約は破棄の旨と理由を明示する。ユーザー指示にも実データ確認にも由来しない設計判断には `[エージェント判断]` を付け、重リスク作業では実装着手前に一覧で報告する。`AGENTS.md` §7の重リスク作業では、仕様を確定した後、実装計画を書く前に仕様レビューを通す。作業中の仮説・試行・次の一手はactive planへ分ける。プロジェクト成立を否定し得る未確認前提は最優先の検証項目として明示し、その結果に依存する作業より先に最小コストで検証する。
