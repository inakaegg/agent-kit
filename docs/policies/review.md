# 独立レビューの詳細規則

共通 `AGENTS.md` §7 の骨子を前提とする。本ファイルはレビューの要否を判断・実施・統括するときに読む。過去の文書やSkillにある gate 1 / gate 2 / gate 3 と「計画レビュー」（gate 2の旧訳）の表記は、それぞれ仕様レビュー・実装計画レビュー・実装レビューを指す。

## レビュー区分

- レビューの重さは変更の種類で決める。**動作に影響しない変更**（誤字・書式・コメント・文書の言い回し）はレビューなしで、CIと自己点検のみとする。**動作に影響する小さな変更**（設定値1つ、規則文書の1段落以内の追記、1関数内の修正など）は実装レビュー1段階だけとする。それ以上は2区分に分ける。**重リスク作業**は、公開API、永続化、並行・非同期状態、認証・security、課金、migration、deploy、または広いarchitectureに関わる変更。**通常対象作業**は、それ以外のユーザー可視動作か、PR化する非自明な変更。重リスクの条件に当たる変更は、大きさによらず重リスク作業とする。

## 各レビューが見るもの

- **仕様レビュー** — 仕様確定後、実装計画の作成前。合格条件、範囲外、停止条件、要件の抜けと矛盾、既存設計文書との未申告の矛盾を見る。実装手段・test構成・CIの細部は実装計画レビュー以降の対象とし、ここでは修正必須にしない。
- **実装計画レビュー** — 実装計画の作成後、実装着手前。方式選定、影響範囲、検証手段、リスクと後戻り可能性を見る。
- **実装レビュー** — 実装と検証の後、commitまたはPR前。差分の正しさと要件充足を見る。

重リスク作業では、実装計画を書く前に仕様レビューを通し、仕様レビュー・実装計画レビュー・実装レビューの各段階を後述の「通過条件」で判定してから次へ進む。通常通過は `VERDICT: LGTM` とし、例外をLGTMと呼ばない。重リスク作業の3段階は統合しない。通常対象作業では、仕様と実装計画を1つのレビューにまとめ、その通過後に実装し、実装レビューを通す（`AGENTS.md` §4・§7）。

## レビュー担当の選び方と待ち方

- レビュー担当は、その成果物を作成・実装した担当とは別の、履歴を共有しない別セッションを必須とする。別のtool/modelは重リスク作業でだけ必須とし、それ以外は呼び出し元のCLIの候補を既定とする（後述の並べ替え）。思考量の既定は `$independent-review` に従い、実装と同じ最高設定を既定にしない。
- **どのモデルを担当にするかは agent-settings のキーで決める。** 重リスク作業（外部操作、課金、security、データ消失、その他 `AGENTS.md` §7の重リスク区分）は `REVIEW_MODEL_HEAVY` を使う。通常対象作業は `REVIEW_MODEL_DEFAULT`、人間向け文書の読みやすさレビューは `REVIEW_MODEL_READABILITY` が示す担当を使う。解決順（kit既定 → 作業repo → local）は `AGENTS.md` §1 のとおり。
- 値は `CLI:MODEL(EFFORT)` を空白区切りで優先順に並べる。CLIは `codex` または `claude`、MODELは実モデル名、EFFORTはそのCLIの思考量で、いずれも省略しない。スキル本文や起動処理へ実モデルと既定思考量を固定しない。`scripts/resolve-agent-model.py` が用途キーから実行argvを解決する。旧形式の系統だけの指定や `any` はモデルが曖昧なため、具体的な候補へ移行する。
- 候補の並びは同じCLI内での優先順とし、どのCLIを先にするかは呼び出し元で決める。resolverは自分が動いているCLI（Claude Codeは `CLAUDECODE`、Codexは `CODEX_THREAD_ID` の環境変数で自動判定。`--primary-cli` で明示できる）と同じCLIの候補を先に試す。Claudeで始めた作業はClaudeの、Codexで始めた作業はCodexの利用枠に寄る。例外は `REVIEW_REQUIRE_OTHER_LINEAGE=true` の重リスク作業で、呼び出し元によらず実装側と別系統を先にする。どちらの環境変数も無いとき（hook、cron、素のshell）と、両方あるとき（一方のCLIからもう一方を起動した入れ子で、内側を判別できない）は並べ替えず設定順のまま使う。入れ子で寄せたいCLIがあれば `--primary-cli` を明示する。この規則の導入前は候補の並びが呼び出し元によらない優先順だった。呼び出し元によらず固定したい場合は `--primary-cli` を明示するか、候補を1つのCLIに絞る。
- CLI未導入は自動で次候補へ進む。起動後の認証不能・明確なモデル利用不可・利用上限は、証跡を残してresolverの `--unavailable` へ渡し、並べ替え後の順で自動フォールバックする。各候補1回までとし、レビュー指摘・検査失敗・一般的な非ゼロ終了・無出力だけでは切り替えない。候補が尽きたら停止し、候補外や追加課金の経路へ広げない。選んだCLI、実モデル、思考量、設定元、並べ替えの根拠（出力の `ordering`: `primary-cli` / `other-lineage` / `configured` と `primary_cli`）、切り替え理由を報告する。
- `REVIEW_REQUIRE_OTHER_LINEAGE=false` では、呼び出し元のCLIを先にした候補順（同一CLI内は指定順）で進め、CodexまたはClaudeの片方だけでも別セッションによるレビューで完了できる。trueの場合は重リスク用途のresolverへ `--implementer-cli` を渡し、別系統を優先する。別系統がすべて利用不能なら同系統を `provisional=true` として選び、後述の暫定通過を適用する。独立した別セッションという条件は、どちらの設定でも維持する。
- full kitではkitの設定を参照し、単体配布のreview関連Skillは同梱のresolverと生成済み設定を使う。配布用コピーは `python3 scripts/sync-model-resolver.py` で正本から生成し、検証時に内容一致を検査する。repoの `agent-settings.env` は既定より優先する。担当関連5キーの値を変える `agent-settings.local.env` は、強弱を推測せず一律に拒否する。
- **担当モデルのキー（`REVIEW_MODEL_*`・`REVIEW_REQUIRE_OTHER_LINEAGE`・`WRITING_MODEL_DEEP` の5キー）の値を変えてよいのは、ユーザーの明示指示があるときだけとする。** エージェントが自分の判断で緩めない。緩めた場合は、変えたキー・値・理由をタスクの契約へ書く。痕跡が残るよう、緩和はgit管理下のenv（kitか作業repoの `agent-settings.env`）で行い、git管理外の `agent-settings.local.env` を緩和に使わない。
- `REVIEW_REQUIRE_OTHER_LINEAGE=true` のあいだ、重リスク作業のレビュー担当は、別系統のモデルが使える限り実装担当と**別系統を必須**とする。別系統が利用上限等で使えないときは、通常対象作業は同系統で進めてよい。重リスク作業は同系統で暫定通過として先へ進み、別系統が使えるようになった時点でその段階をやり直す。暫定通過の事実とやり直しの残件をタスクの契約へ書き残す。
- 暫定通過中の重リスク作業は「必要なレビューをすべて通した」状態に当たらない。`AUTO_MERGE_PRIVATE=true` による許可なしのローカルmergeは、やり直しが済むまで行わない。
- 複数エージェントの並行体制では、当該成果物を作っていない側がレビューを起動・統括することを既定とし、同じ段階のレビューを両側から二重起動しない。
- 起動済みのレビュー担当は無出力だけでは失敗と判定せず、明示的なerror、process終了、設定不備が確認できない限り最低30分待つ（中断は途中までの推論tokenを捨て、再実行で二重消費する）。
- レビュー担当へ渡すのは、タスク契約、関連仕様、同じ機能を扱う既存の設計文書・対応表、当該段階の成果物（仕様、実装計画、baseとの差分）、検証結果、必要な資料であり、実装者の仮説・期待・弁明は渡さない。

## 指摘の出し方

- 規則・文書のレビューでは、前提となるOS、ツール、symlink等の導入状態を挙げ、その前提がない新規導入環境や片方のツールだけの環境でも使えるかを確認する。
- レビュー担当は成果物を変更しない。確認済みの正しさ・security・データ消失・互換性・明示要件違反（合格条件の検証不能を含む）は、修正必須として重大度順にすべて報告する。報告数・修正必須数の上限から除外し、件数だけで省略・記録扱いにしない。
- それ以外は重大度順に最大5件とし、読みやすさだけの修正必須はそのうち最大2件、残りは記録のみとする。文体の好みや根拠のない懸念を修正必須にしない。
- 既存設計文書との矛盾と根拠を成果物が明示していなければ、細部より優先して修正必須とする。
- 各指摘には場所、失敗する入力・状態・経路、違反する要件を付ける。最後に `VERDICT: LGTM` または `VERDICT: CHANGES REQUESTED` を出す。

## 指摘の受け方と回数

- 指摘は修正・記録のみ・反証へ仕分ける。再現、失敗test、失敗経路のいずれでも裏付けられない指摘を修正必須にしない。
- 修正後は影響する検査を再実行し、新しいセッションで修正差分と関連箇所をレビューする。省略できる場合は下の通過条件だけで判断する。
- 必要資料を読めて `VERDICT` まで出した完了レビューだけを回数に数える。tool failure、対象違い、必要資料不足、`VERDICT` 欠落は未完了とし、原因を直して再実行する。
- 各段階は2回を既定とする。1回目は全体、2回目は前回の修正必須の解消と修正差分を見る。新規指摘も、確認済みの正しさ・security・データ消失・互換性・明示要件違反なら修正必須とし、回数だけで格下げしない。それ以外の新規指摘は記録のみとする。
- 同じ修正必須が新しい証拠なく反復する場合は、回数を重ねず人間判断へ戻す。同型の有効な指摘が2件以上あれば、lint、test、type、Hook、CIで検出できる部分を機械化する。

## 通過条件

判定の正本は本節とする。本節の「重大な修正必須」は、確認済みの正しさ・security・データ消失・互換性・明示要件違反（合格条件の検証不能を含む）の5分類を指す。自己検証を禁止する3分類とは区別する。まずレビューが完了していることを確認し、その後に下表を使う。未完了レビュー、未確認の解消、利用不能、経過時間を通過理由にしない。

| 状態・条件 | 次の行動と記録 |
|---|---|
| 修正後の成果物に `VERDICT: LGTM` がある | 通常通過。その段階を終了する |
| コード変更を含まない文書・計画で、全修正必須の事実を実データで裏取りして修正し、該当検査と修正差分の点検を済ませた | 再レビューを省略し「自己検証による例外通過」と記録してよい。ただしsecurity・データ消失・互換性破壊に関わる指摘は省略不可 |
| 2回終了後、上記の重大な修正必須がなく、軽微な残指摘だけがある | 残件を課題にして「記録付き例外通過」と記録する |
| 2回終了後も上記の重大な修正必須が残る | 修正・再検査後、新しい独立セッションで解消確認を1回だけ追加する。LGTMが得られなければ停止して人間判断へ戻す |
| 公開・提出する人間向け文書の読みやすさレビュー | 上の例外通過は適用せずLGTMを得る。2回目で新たな初見読者の目的不達があれば、修正後の解消確認を1回追加できる。重大な修正必須も追加確認の対象。いずれも追加は計1回までで、なおLGTMが得られなければ停止する |

通常のコード修正は自己検証による例外通過の対象外であり、独立した再レビューを要する。2回終了時の重大指摘の解消は、修正した本人の申告だけで通過させない。

別系統が利用不能な重リスクレビューは、上表の通過理由に加えて「同系統による暫定通過」を記録し、復旧後に該当段階をやり直す。これは自己検証・記録付き例外通過とは別の制約であり、どちらかの記録で他方を省略しない。

実在するreview verdict、通過理由、修正・再検査の証跡、残件、暫定通過の有無を分けて報告する。自己検証や残件記録を、実在しない `VERDICT: LGTM` として報告しない。`AUTO_MERGE_PRIVATE=true` による許可なしmergeは、必要なレビューすべてのLGTMと暫定通過のやり直し完了を要し、自己検証・記録付き例外通過では行わない。

## PR bot指摘の扱い

P0・P1相当、および確認済みの正しさ・security・データ消失・互換性・明示要件違反は修正必須とする。それ以外のP2以下は後続の課題にする。反復は2巡を既定とし、3巡目以降の軽微指摘は課題にして収束させるが、上記の修正必須を優先度・件数・巡回数だけで格下げしない。修正必須が残れば解消を確認してから収束させ、対応不能なら停止する。権限と詳細手順は `$pr-review-loop` に従う。

## GitHub上の反復

GitHub bot・CIを含む反復は `$pr-review-loop` に従う。最新head、対応が必要な全指摘、required CIを確認し、沈黙・rate limit・経過時間を承認とみなさない。bot reviewの反復は2巡までとし（上記の仕分け既定）、この回数は各段階のローカルレビューの回数とは別に数える。mergeは `AGENTS.md` §3のとおり明示許可を必要とする（`AUTO_MERGE_PRIVATE=true` の非公開・非共有repositoryでは、必要なレビューがすべてLGTMなら許可不要）。
