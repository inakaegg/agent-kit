# 独立レビューの詳細規則

共通 `AGENTS.md` §7 の骨子を前提とする。本ファイルはレビューを実施・統括するときだけ読む。過去の文書やSkillにある gate 1 / gate 2 / gate 3 と「計画レビュー」（gate 2の旧訳）の表記は、それぞれ仕様レビュー・実装計画レビュー・実装レビューを指す。

## 各レビューが見るもの

- **仕様レビュー** — 仕様確定後、実装計画の作成前。合格条件、範囲外、停止条件、要件の抜けと矛盾、既存設計文書との未申告の矛盾を見る。実装手段・test構成・CIの細部は実装計画レビュー以降の対象とし、ここでは修正必須にしない。
- **実装計画レビュー** — 実装計画の作成後、実装着手前。方式選定、影響範囲、検証手段、リスクと後戻り可能性を見る。
- **実装レビュー** — 実装と検証の後、commitまたはPR前。差分の正しさと要件充足を見る。

重リスク作業でも、仕様と実装計画が1つの短い文書に収まる場合は、仕様レビューと実装計画レビューを1回へ統合してよい。統合レビュー1回の `VERDICT: LGTM` で両方の通過とする。

## レビュー担当の選び方と待ち方

- レビュー担当は、その成果物を作成・実装した担当とは別の、履歴を共有しない別セッションを必須とし、可能なら別のtool/modelを使う。思考量の既定は `$independent-review` に従い、実装と同じ最高設定を既定にしない。
- **どのモデルを担当にするかは agent-settings のキーで決める。** 重リスク作業（外部操作、課金、security、データ消失、その他 `AGENTS.md` §7の重リスク区分）は `REVIEW_MODEL_HEAVY` を使う。通常対象作業は `REVIEW_MODEL_DEFAULT`、人間向け文書の読みやすさレビューは `REVIEW_MODEL_READABILITY` が示す担当を使う。解決順（kit既定 → 作業repo → local）は `AGENTS.md` §1 のとおり。
- 値は「系統」または「系統(思考量)」を空白区切りで**先頭からの優先順**に並べたものとする。系統名は固定語彙ではなくtool/model系統の自由なラベル（例: `codex` / `fable` / `opus`）で、新モデルは設定値に名前を書けば使える。`any` は系統を問わない（履歴を共有しない別セッションであればよい）。値が矛盾している場合（値が空、`REVIEW_REQUIRE_OTHER_LINEAGE=true` なのに実装担当と同系統しか並んでいない等）は、推測せず `AGENTS.md` §10 に従って停止しユーザーへ確認する。
- **担当モデルのキー（`REVIEW_MODEL_*`・`REVIEW_REQUIRE_OTHER_LINEAGE`・`WRITING_MODEL_DEEP` の5キー）の値を変えてよいのは、ユーザーの明示指示があるときだけとする。** エージェントが自分の判断で緩めない。緩めた場合は、変えたキー・値・理由をタスクの契約へ書く。痕跡が残るよう、緩和はgit管理下のenv（kitか作業repoの `agent-settings.env`）で行い、git管理外の `agent-settings.local.env` を緩和に使わない。
- `REVIEW_REQUIRE_OTHER_LINEAGE=true` のあいだ、重リスク作業のレビュー担当は実装担当と**別系統のモデルを必須**とし、同系統での代替は開示付きの一時fallbackとしても認めない。設定が示す担当が使えない場合はその段階のレビューを保留し、待つか・設定を変えるか・中止かをユーザーへ諮る。
- 設定を緩めて実施したレビュー、および過去に同系統で実施したレビューは、標準の担当が使えるようになった時点でやり直しの対象になる。その旨をタスクの契約へ書き残す。
- 複数エージェントの並行体制では、当該成果物を作っていない側がレビューを起動・統括することを既定とし、同じ段階のレビューを両側から二重起動しない。
- 起動済みのレビュー担当は無出力だけでは失敗と判定せず、明示的なerror、process終了、設定不備が確認できない限り最低30分待つ（中断は途中までの推論tokenを捨て、再実行で二重消費する）。
- レビュー担当へ渡すのは、タスク契約、関連仕様、同じ機能を扱う既存の設計文書・対応表、当該段階の成果物（仕様、実装計画、baseとの差分）、検証結果、必要な資料であり、実装者の仮説・期待・弁明は渡さない。

## 指摘の出し方

- 規則・文書のレビューでは、成果物が前提にする環境・導入形態（OS、ツール、symlinkなど導入手順の完了状態）を挙げ、その前提を持たない読者・環境（一方のツールしか使わないユーザー、新規導入直後など）でも記述が成り立つかを確認する。
- レビュー担当は成果物を変更せず、再現可能な正しさ・security・データ消失・互換性・要件違反だけを、重大度順に最大5件報告する。修正必須の指摘はそのうち最大2件とし、残りは記録のみの指摘とする。
- 成果物が渡された既存設計文書と矛盾するのに、矛盾と根拠を明示していない場合は、細部より優先して修正必須とする。
- 各指摘に場所、失敗する入力・状態・経路、違反する要件を付け、最後に `VERDICT: LGTM` または `VERDICT: CHANGES REQUESTED` を出す。

## 指摘の受け方と回数

- 指摘は盲目的に適用せず、**修正 / 記録のみ / 誤検知として反証** へ仕分ける。再現、失敗test、失敗経路のいずれでも裏付けられない指摘を修正必須として扱わない。
- 修正必須の指摘を直した後は影響する検査を再実行し、修正後の成果物に対してその段階のレビューを新しいセッションでやり直す。ただし成果物がコード変更を含まない文書・計画で、全修正必須の指摘の事実関係を実データで裏取りして修正した場合は、やり直しを省略し自己検証（該当検査の再実行と修正差分の点検）で代えてよい。security・データ消失・互換性破壊に関わる修正必須の指摘はこの省略の対象外とする。
- 回数として数えるのは、必要資料を読めて `VERDICT` 行まで出した完了レビューだけとし、tool failureや `VERDICT` 欠落は数えない。
- `VERDICT: LGTM` が出た時点でその段階のレビューを終了する。各段階のレビューは2回までを既定とする。1回目は全体を見る。2回目は前回の修正必須の解消と修正差分の確認を主対象とし、新たに出た指摘はsecurity・データ消失・互換性破壊を除き記録のみとする。
- 2回目の終了時にLGTMでない場合、security・データ消失・互換性破壊の修正必須が残るなら人間判断へ戻す。それ以外の残指摘だけなら記録のみとして通過とし、完了報告へ明記する。回数を追加できるのは、この重大3種を修正した後の解消確認1回だけとする。ただし人間向け文書の読みやすさレビュー（`$docs-maintenance`）では、2回目で新たに「初見読者の目的不達」の修正必須が出た場合に限り、修正後の解消確認を1回追加できる。
- 同じ修正必須の指摘が新しい証拠なく繰り返される場合は、回数を重ねず人間判断へ戻す。
- 同型の有効な指摘が2件以上あれば、lint、test、type、Hook、CIのいずれかへ機械化する。

## GitHub上の反復

GitHub bot・CIを含む反復は `$pr-review-loop` に従う。最新head、対応が必要な全指摘、required CIを確認し、沈黙・rate limit・経過時間を承認とみなさない。最大5回で停止する。この回数は各段階のローカルレビューの回数とは別に数える。mergeは `AGENTS.md` §3のとおり明示許可を必要とする（`AUTO_MERGE_PRIVATE=true` の非公開・非共有repositoryでは、必要なレビューがすべてLGTMなら許可不要）。
