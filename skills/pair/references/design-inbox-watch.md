# 設計ノート — Codex実装役のinbox-watchと、採らなかった代替案

サマリー:

- 相手がCodexのときのpairの通信方式を「transport C」と呼ぶ（CはCodexの頭文字。
  実体は `transport-codex.md` に定めた、inbox/outboxファイルでのやりとり）。
- Codexはユーザーが話しかけたときだけ動く（ターン駆動）。そのためtransport Cの初版では、
  監視役が指示を書くたびにユーザーがCodexへ「inbox確認して」と打つ必要があった。
- 対策として、実装役は返事待ちのあいだターンを終えず、shellのsleepループでinboxの
  更新を見張り続けるようにした（inbox-watch。1回約5分×最大6回。それでも指示が来なければ
  ターンを終え、以後は従来どおりユーザーに促してもらう）。
- 待っているあいだのトークン消費はゼロ。消費するのは約5分ごとにwatchをかけ直す一瞬だけで、
  回数に上限がある。
- 「watchのon/off設定」「チャット履歴を常時読み合う旧方式への回帰」「cronでの定期起動」は
  いずれも検討のうえ採らなかった。理由は本文のとおり。
- ひとことで言えば、初代pairが持っていた「相手が書き込めば自動で動き出す」性質を、
  安上がりな形でCodex相手にも取り戻した変更である。

以下は判断の詳細。skill本体を改訂するときに読む。実行時にagentが読む必要はない。

## 歴史背景

1. **初代（チャット履歴を読み合う方式）** — 初期のpairは、Codex/Claudeの区別なく、
   お互いが相手のチャット履歴ファイル（Claudeはセッションjsonl、Codexはrollout）を
   定期的に読んで反応していた。相手が書き込めば自動で動き出す反面、履歴の中身を
   読み続けるためトークン消費が大きかった。
2. **SendMessageへの移行（Claude同士）** — その後Claude Codeにセッション間の
   メッセージ送信機能（SendMessage/ListAgents）が実装され、Claude同士は
   「届いたら起こしてもらう」プッシュ型になった。読み続ける必要がなくなり、
   トークン消費が大きく減った。
3. **transport Cの初版（Codex相手）** — CodexはSendMessageの仕組みに参加できないため、
   Codex相手専用の通信方式として、合意ファイル（inbox/outbox）とrollout監査による
   やりとりを新設した（これがtransport C）。ただこのとき、
   Codexを動かす手段を「ユーザーがCodexチャットへ一言打つ」だけにしてしまい、
   初代が持っていた自動性を失った。
4. **inbox-watch（本設計）** — その自動性を、履歴を読み合う方式へ戻るのではなく、
   「ターンを終えずにファイルの更新を見張る」形で取り戻した。

## 問題

Codex CLIはターン駆動で、ターンが終わるとユーザーが話しかけない限り次のターンが
始まらない。transport Cの初版では、gateの判定・指摘の受け渡し・docsの受け渡しの
たびにユーザーの手動操作が挟まり、2チャット体制の意味が薄れるほど煩雑だった。

## 採った設計: ターンを終えない見張り（inbox-watch）

実装役は、監視役への報告を書いたあとターンを終えず、inboxファイルの更新時刻を
確認するsleepループをshellで実行する。1回あたり約5分、更新がなければかけ直し、
合計約30分待っても指示が来なければターンを終える。ターンが終わったあとは
従来どおり、ユーザーにCodexチャットで一言促してもらう。

この設計の根拠はトークン消費の内訳にある。

- sleepで止まっているあいだ、モデルは何も処理していない。待ち時間そのものの消費はゼロ。
- トークンを消費するのは、sleepループが終わってモデルに制御が戻る一瞬だけ。
  約5分ごとに「更新なし→もう一度見張る」という小さな処理が入る。会話の文脈は
  キャッシュが効くため、1回あたりの実費は小さい。
- かけ直しは最大6回で打ち切るので、返事が来ない場合の消費にも上限がある。

つまり1回の待機で余分にかかるのは「小さな処理が最大6回」だけであり、
毎回の手動操作をなくす対価としては十分安い。

## 採らなかった代替案

### watchのon/off設定を設ける

採らなかった。「off相当」は設定ではなく自動で起こるからである。watchのコマンドが
実行のたびに承認を求められる環境や、タイムアウトで切られる環境では、実装役が
その旨をoutboxへ書いてターンを終え、以後は従来どおりユーザーに促してもらう運用へ
切り替わる。つまり「offにすべき環境かどうか」は実行時にわかることで、ユーザーが
事前に選ぶ必要がない。設定にすると起動のたびに確認が増え、指示書も分岐して、
得るものがない。

### チャット履歴を読み合う初代方式へ戻す

採らなかった。理由は2つ。

1. 監視役(Claude)側の「見張り続ける」は、ファイルの更新があったときだけ起こして
   もらう仕組み（Monitor等）で、すでに実質無料で実現できている。初代方式との違いは
   「履歴の中身を常に読むか、変化があったときだけ要点を読むか」だけで、
   常に読む方式は同じ情報に余分なトークンを払う。
2. 履歴を全部読む必要がある場面（開始宣言の裏取り、gate前の判断過程の確認、
   報告と実物が食い違ったとき）は、その都度の監査として行う設計になっている。
   常時監視にしても見つけられる問題は増えない。

### cron等でCodexを定期的に起動する

採らなかった。外から定期的に起動する方式は、起動のたびに会話全体を読み込む推論が
走るため、sleepループのかけ直しよりも高くつく。ファイル更新をきっかけに動く
今の方式で足りる。

## 将来の改善候補

- 見張り1回あたりの時間を延ばす。実装役の環境でコマンドの実行時間制限が長いことを
  確かめられたら、5分×6回を10分×3回などにすると、トークンを消費するかけ直しの回数が
  半分になる。これは設定項目ではなく既定値の改善として入れる。

## 制約（承知のうえで受け入れているもの）

- 見張りはターンと一緒に終わる。30分の上限を超えたあとや、実装役が停止条件に
  達したあとは、ユーザーの一言が必要になる。
- 更新時刻だけを見ているので、inboxに書かずに何かを伝える手段はない（これは利点でも
  ある。やりとりが必ずファイルに残り、あとから監査できる）。
- コマンドごとに承認が要る環境ではwatchは成立しない。承認を回避する仕組みは作らず、
  手動運用に切り替える。
