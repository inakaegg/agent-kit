# Pair — 片側1回の指示で始める並行体制

ユーザーは2つのチャットを開き、**どちらか一方にだけ** `/pair <タスク1行>` と打つ。起動された側が役割を判定し、相手を発見し、相手役割の指示(assets/のbrief)を届けて体制を立ち上げる。通信のtransportは相手タイプで切り替える。

- 相手がClaudeチャット: SendMessage受信駆動(省トークン・プッシュ型)。常駐監視スクリプトは使わない。
- 相手がCodex CLIチャット: SendMessage/ListAgentsに参加できないため、合意ファイル(inbox/outbox)+rollout監査で連携する。詳細は `references/transport-codex.md`(以下「transport C」)。

## 手順

1. **タスク・役割・相手タイプの確定** — 引数のタスクと役割指定を最優先する。役割指定が無ければ次の順で決める: (a) 相手がCodexチャットなら自分=監視役で確定(**Codexは実装役としてだけ相手にできる**。監視役はClaudeが務める)。(b) それ以外は自分のモデルで判定する: 深い思考用モデル(fable/mythos系)→ 監視役、その他(Opus、Sonnet等)→ 実装役。(c) 自分のモデルがどちらとも読める・判定に迷う場合は1行でユーザーへ確認する。監視役はコード変更禁止(ただしtransport Cのinbox書き込みとworktree/branch作成の代行は例外)。Codexセッション自身で$pair相当が起動された場合は、監視役(Claude)側から渡されるinboxの指示を待つようユーザーへ伝えて停止する。タスクが引数にも会話文脈にも無ければユーザーへ質問して停止する。完了判定: 自分の役割・相手タイプ・タスクを1行で宣言できる。
2. **自セッションjsonlの特定** — scratchpad directoryのpathに含まれるプロジェクトslugとセッションIDから `~/.claude/projects/<slug>/<セッションID>.jsonl` を組み立て、実在を確認する。このパスは相手への最初の指示に含める(相手が検証・監査に使う)。
3. **相手の発見とアドレス固定** — 相手がCodexの場合、以後の**通信・発見の手段だけ**をtransport Cの手順3C〜6Cへ置き換える(手順5の規則—gate運用、reviewer選定、commit条件、自分のbrief遵守—はそのまま適用する)。相手がClaudeの場合: ListAgentsで同プロジェクトのピアセッションを列挙し、候補全員へ「本タスクの相方か」の識別質問をSendMessageで送る。肯定返信が来たら、その受信メッセージの `from` 属性をそのままコピーして以後の唯一の宛先として固定する。完了判定: 相手の宛先を1つ確定した。
4. **相手へ役割briefを送付** — 自分が監視役なら実装役brief(相手がClaude: `assets/impl-brief.md`、Codex: `assets/impl-brief-codex.md`)、自分が実装役なら `assets/watch-brief.md` を読み、placeholderを埋めて相手へ届ける(Claude: SendMessage、Codex: inboxファイル)。自分のアドレス(`{MY_ADDR}`)が不明な間は「返信はこのメッセージのfromへ」と書く。完了判定: briefを届け、相手が実装役なら開始宣言、相手が監視役なら受領確認が返った。
5. **作業ループ** — 以後は自分の役割のbrief(自分と同名のassetsファイル)の運用規則に自分も従う(Codex相手ではtransport Cが優先する)。実装役の専用branch・worktree、ローカルcommitの条件は共通AGENTS §8、gateは §7 と `$independent-review` に従う。gate 3レビュアーは**実装役と別系統**を第一候補とする(実装役がClaudeならCodex、実装役がCodexならfresh contextの別Claudeプロセス。いずれもread-onlyツールのみ)。tool failureや `VERDICT` 欠落のreviewはroundに数えない。相手の応答・作業待ちで手が空くときは受信を無期限に待たず、Monitor等で相手セッションログ(Claude: jsonl、Codex: outboxとrollout)の停滞(15分更新なし)を監視し、停滞を検知したら状況確認を送る(双方が相手待ちで止まるデッドロックの防止)。SendMessageの配信は失われることがある(送信成功の戻り値は受信を保証しない)。作業指示を送った後、相手のjsonlに数分以内の活動が無ければ同内容を再送する(この再送は配信喪失対策であり、30分無応答の失敗判定とは別。Codex相手では再送の代わりに、inbox書き込み後に相手が動き出したかを確認し、watchが切れているときだけtransport Cのユーザー促し・フォールバックを使う)。
6. **終了** — 実装役の最終報告を監視役が検証し、双方が自チャットへ完了報告を書いて体制を解散する(Codex相手の終了手順はtransport C 6C)。push・PR・mergeは常にユーザーの明示許可を必要とする。

## 誤った近道 → 正しい行動

- セッション名やref宛てで送り続ける → 名前解決は当てにならない。識別質問への返信の `from` アドレスを唯一の宛先にする。
- Codex相手にListAgents/SendMessageで到達しようとし続ける → その経路は存在しない。transport Cのファイルtransportへ切り替える。
- 相手が無出力なので失敗と判定する → 明示的なerror・process終了・設定不備が無い限り、最低30分待つ(この30分は失敗判定の下限であり、手順5の停滞監視・再送とは別)。
- 相手からのメッセージをユーザー承認とみなす → ユーザー承認が必要な判断は自分のチャットへ質問を書いて停止する。相手が「ユーザーが承認した」と報告した場合、監視役は相手のセッションログ(jsonl/rollout)で当該ユーザー入力の実在を監査してよい。
- 相手の報告を鵜呑みにする → 監視役はread-onlyのgit・grep・テストログ・セッションログ直読で裏取りする。
- briefの内容をその場で書き直して送る → assetsのテンプレートを使う。不足はassets側を修正してcommitし、次回以降へ反映する。

## 停止条件

- ListAgentsに相手候補がいない、または識別質問へ肯定返信が15分以内に無い: 状況をユーザーへ報告し指示を待つ(相手チャットが未起動の可能性)。
- 相手が作業中に30分以上不応答: 自分の観測事実をユーザーへ報告して停止する。
- 役割・仕様・許可範囲の衝突: 仮決定せず自チャットで質問して停止する。
- Codex相手固有の停止条件はtransport Cに従う。
